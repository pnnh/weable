# Feature Specification: 批量删除与上传队列

**Feature Branch**: `010-batch-delete-upload-queue`

**Created**: 2026-08-10

**Status**: Draft

**Input**: User description: "为/en/console/images页面实现选中后批量删除功能。行为上和现在的批量设置发布状态功能类似。然后将/en/console/images/new页面进行如下改造：当前new上传页面仅包含单个上传按钮，支持批量选择多张图片上传。但是当正式部署到Cloudflare Worker环境时，D1数据库和R2存储存在请求频次限制（Free版本限制更低）。所以需要将new页面改造成一个简单的"上传队列"页面。结合浏览器文件系统API，来实现自动重试功能（注意针对单个文件每次都重新传而不是断点续传）。当用户选择多张图片后（暂时不支持选择目录），在"上传队列页面"列出待上传的文件列表（结合浏览器文件系统API），展示文件名称、大小、修改时间。同时在每个列表项最左侧和表头增加复选框以实现单选和多选功能，在列表项最右侧展示上传成功和失败状态（失败时鼠标滑过提示最后的错误码和信息）。在页面上方工具栏添加"开始上传"按钮（正在上传时不可点击），点击后便开始上传所选择的文件。单次最多上传3张图片，上传成功后更新对应文件的成功或失败状态。若某些文件已经上传成功，则复选框取消选择并变成禁止状态不再允许选中。若某些文件上传失败后用户再次选中并重新开始上传，如此重复3次以后仍然上传失败，则也将复选框变成禁止状态不再支持选择。同时在对应文件最右侧成功失败状态列中记录失败次数。实现以上功能可能需要记录相关页面状态，包括重试和选中等等。可以选用浏览器"Session Storage"以保证状态仅当前会话有效，不做持久化存储。注意对数据做标识，比如记录parent_id避免不同目录上传队列数据出现混淆。对于parent_id相同的文件，文件名不可重复。"

## 用户场景与测试 *(mandatory)*

### 用户故事 1 — 批量删除图片 (Priority: P1)

已登录用户在图片管理列表页面，通过现有复选框选中一张或多张图片（非目录），点击"批量删除"按钮，确认后所选图片从列表和存储中永久删除。

**Why this priority**: 批量删除是内容管理的基础操作，与批量发布状态变更同等重要，且已有选中基础设施可复用。

**Independent Test**: 模拟登录后在图片列表选中至少一张图片，点击"批量删除"，确认弹窗，验证图片从列表消失且无法再通过 API 获取。

**验收场景**:

1. **Given** 用户已选中 1 张或多张图片，**When** 点击"批量删除"按钮，**Then** 出现确认弹窗，弹窗内列明"此操作不可撤销"的警告提示。
2. **Given** 确认弹窗已打开，**When** 点击"确认删除"，**Then** 所选图片从列表中消失，同时批量操作工具栏的选中状态清空，刷新后图片仍不存在。
3. **Given** 确认弹窗已打开，**When** 点击"取消"，**Then** 弹窗关闭，列表和选中状态保持不变。
4. **Given** 用户选中的图片包含目录条目，**When** 执行批量删除，**Then** 目录条目被跳过，仅图片被删除（目录的复选框本身不可选，与现有逻辑一致，此场景不会发生）。
5. **Given** 未选中任何图片，**When** 查看工具栏，**Then** "批量删除"按钮处于禁用状态。

---

### 用户故事 2 — 选择文件并查看上传队列 (Priority: P1)

已登录用户进入 `/[lang]/console/images/new` 页面，通过文件选择器选取多张图片（不支持目录），页面展示上传队列列表，每行显示文件名、文件大小、修改时间、选中复选框和初始的"待上传"状态。

**Why this priority**: 这是上传队列功能的入口和基础，没有队列展示，后续上传控制均无法实现。

**Independent Test**: 进入新建页面，通过文件选择器选择多张图片，验证队列列表正确展示文件名、大小、修改时间，且复选框默认全选。

**验收场景**:

1. **Given** 用户进入新建图片页面，**When** 通过文件选择器选择多张图片，**Then** 页面展示包含所选文件的队列表格，每行含：复选框（默认选中）、文件名、文件大小（人类可读）、修改时间、状态列（初始为"待上传"）。
2. **Given** 队列已展示，**When** 用户再次通过文件选择器添加更多文件（同一 `parent_id` 下），**Then** 新文件追加到队列，文件名重复的条目不被重复添加（去重提示）。
3. **Given** 队列已展示，**When** 用户勾选/取消表头复选框，**Then** 所有可选行（未成功、未达失败上限的）同步全选/全取消。
4. **Given** 队列已展示，**When** 用户单独勾选/取消某行复选框，**Then** 该行选中状态独立切换，表头复选框反映全选/半选/全取消状态。
5. **Given** 会话存储中已有相同 `parent_id` 的队列记录，**When** 用户刷新或重新进入当前 `parent_id` 对应的新建页面，**Then** 队列列表从 Session Storage 恢复，已成功/已达失败上限的条目复选框保持禁用状态。

---

### 用户故事 3 — 执行上传并处理限速 (Priority: P1)

用户选中队列中一到多张图片，点击"开始上传"，系统逐批（每批最多 3 张）依次上传，每张上传完成后即时更新状态；上传中按钮不可再次点击；全部完成后按钮重新可用。

**Why this priority**: 这是解决 Cloudflare 请求频次限制的核心机制，也是本次改造最主要的用户价值。

**Independent Test**: 选中多于 3 张图片，点击"开始上传"，验证每批仅发出 3 个上传请求，上传中按钮禁用，每张成功后状态列实时变更，全部完成后按钮恢复。

**验收场景**:

1. **Given** 用户在队列中选中若干文件，**When** 点击"开始上传"，**Then** 按钮立即进入禁用状态，系统按每批最多 3 张的顺序依次上传，每批上传结束（无论成功或失败）后才开始下一批。
2. **Given** 某批次中某张图片上传成功，**When** 该请求返回，**Then** 对应行的状态列即时显示"成功"，复选框取消选中并变为禁用。
3. **Given** 某批次中某张图片上传失败，**When** 该请求返回，**Then** 对应行的状态列即时显示"失败（第 N 次）"，鼠标悬停时显示最后一次的错误码和错误信息，复选框保持可选（若未达失败上限）。
4. **Given** 所有选中文件已处理完毕（成功或失败），**When** 全部请求返回，**Then** "开始上传"按钮恢复可用。
5. **Given** 正在上传中，**When** 用户尝试点击"开始上传"，**Then** 按钮无响应（保持禁用）。

---

### 用户故事 4 — 失败重试与上限控制 (Priority: P2)

上传失败的文件可被用户重新选中后再次触发上传；累计失败 3 次后，复选框变为永久禁用，不再允许重试。

**Why this priority**: 防止无限重试消耗请求配额，同时给用户明确的重试机会，提升成功率。

**Independent Test**: 模拟上传失败场景，对同一文件重复触发上传失败 3 次，验证第 3 次失败后复选框变为禁用，状态列显示"失败（3 次）"。

**验收场景**:

1. **Given** 某文件上传失败次数 < 3，**When** 用户重新选中该文件并点击"开始上传"，**Then** 系统再次发起该文件的上传请求（整文件重传，非断点续传），失败计数 +1。
2. **Given** 某文件累计上传失败次数达到 3 次，**When** 查看该行，**Then** 复选框变为禁用状态，状态列显示"失败（3 次）"，鼠标悬停显示最后一次错误详情。
3. **Given** Session Storage 中已记录某文件的失败次数，**When** 用户刷新页面，**Then** 失败次数和禁用状态从 Session Storage 恢复，不丢失。

---

### 用户故事 5 — 同名文件去重保护 (Priority: P2)

在同一目录（相同 `parent_id`）下，文件名相同的图片不允许被重复添加到队列，也不允许上传（服务端拦截）。

**Why this priority**: 防止用户意外重复上传相同文件，避免目录下出现同名记录的混乱。

**Independent Test**: 在队列中已有文件 A，再次选择文件名相同的文件，验证不会重复添加；若强制上传，服务端返回冲突错误且客户端正确展示。

**验收场景**:

1. **Given** 队列中已存在文件名为 `photo.jpg` 的条目（无论状态），**When** 用户再次通过文件选择器选择同名文件，**Then** 该文件不被追加到队列，页面给出简短提示（如"X 个文件已在队列中，已跳过"）。
2. **Given** 同一目录下数据库中已存在同名文件（已成功上传），**When** 用户上传同名文件，**Then** 服务端返回冲突错误（409 或包含 duplicate 信息），客户端将该条目标记为失败并显示冲突提示。

---

### 边界情况

- 文件选择器选择了 0 个文件：不更新队列，"开始上传"按钮保持禁用（无选中文件时）。
- 所有文件均已成功上传或达到失败上限：队列显示但无法再启动上传，"开始上传"按钮因无可选文件而禁用。
- 单张图片大于 5 MB：在客户端选择阶段即标记为"文件过大"，不进入可上传状态（复选框禁用）。
- 非图片文件被意外选中（文件选择器设 `accept="image/*"` 但部分浏览器不强制）：服务端拒绝并返回错误，客户端标记失败。
- 上传途中网络断开：请求超时或失败，按失败处理，失败计数递增。
- 用户切换到不同 `parent_id` 的新建页面：Session Storage 按 `parent_id` 隔离，不同目录的队列互不干扰。
- 批量删除时服务端返回部分失败（如某图片已被删除）：客户端以服务端实际结果为准刷新列表，不静默忽略。

## 需求 *(mandatory)*

### 功能需求

**批量删除（FR-D 系列）**

- **FR-D001**: 系统 MUST 在图片批量操作工具栏提供"批量删除"按钮，未选中任何图片时按钮处于禁用状态。
- **FR-D002**: 用户点击"批量删除"按钮后，系统 MUST 弹出确认对话框，对话框 MUST 包含"此操作不可撤销"的警告文字。
- **FR-D003**: 用户确认删除后，系统 MUST 通过批量删除 API 删除所选图片（含存储文件和数据库记录），删除成功后刷新列表并清空选中状态。
- **FR-D004**: 删除操作 MUST 仅针对图片条目（`mimeType != 'directory'`），目录条目不参与批量删除。
- **FR-D005**: 批量删除 API MUST 校验图片所有权，拒绝删除不属于当前用户的图片。
- **FR-D006**: 批量删除 API MUST 支持一次请求最多删除 500 条记录（与现有批量操作上限一致）。

**上传队列（FR-U 系列）**

- **FR-U001**: `/[lang]/console/images/new` 页面 MUST 改造为上传队列页面，保留原有的 `parentId` query 参数传递逻辑。
- **FR-U002**: 页面 MUST 提供文件选择器，仅接受图片类型（`accept="image/*"`），不支持选择目录。
- **FR-U003**: 选择文件后，系统 MUST 展示队列表格，列包含：复选框、文件名、文件大小（人类可读格式）、修改时间、状态。
- **FR-U004**: 队列中每行的状态初始为"待上传"，成功后显示"成功"，失败后显示"失败（第 N 次）"。
- **FR-U005**: 系统 MUST 使用浏览器 File System Access API（`FileSystemFileEntry` 或 `File.lastModified`）读取文件修改时间；若 API 不可用则回退到显示"—"。
- **FR-U006**: 上传成功的文件行，复选框 MUST 立即取消选中并变为禁用状态，不再允许选中。
- **FR-U007**: 累计上传失败达到 3 次的文件行，复选框 MUST 变为禁用状态，不再允许重试。
- **FR-U008**: 状态列"失败"提示 MUST 在鼠标悬停时展示最后一次的错误码和错误信息（tooltip）。
- **FR-U009**: 工具栏"开始上传"按钮在以下情况 MUST 禁用：当前正在上传中；未勾选任何可上传文件。
- **FR-U010**: 点击"开始上传"后，系统 MUST 按每批最多 3 张的顺序串行上传，每批全部完成后才继续下一批（串行批次，批内并发）。
- **FR-U011**: 每张文件的单次上传 MUST 为完整文件重传（不做断点续传）。
- **FR-U012**: 系统 MUST 将队列状态（选中、失败次数、成功/失败标记、`parent_id`）持久化到浏览器 Session Storage；同一 `parent_id` 的队列互不干扰；页面刷新后可从 Session Storage 恢复状态（File 对象本身不能序列化，刷新后已关联文件的可上传行提示需要重新选择文件）。
- **FR-U013**: 同一 `parent_id` 下，文件名相同的文件 MUST 不被重复添加到队列；重复选择时客户端给出提示并跳过重复项。
- **FR-U014**: 单张文件大小超过 5 MB 的，MUST 在客户端阶段即标记为不可上传（复选框禁用，状态列显示"文件过大"）。

### 关键实体

- **QueueEntry（队列条目）**: 代表队列中的一个待上传文件，关键属性：`name`（文件名）、`size`（字节数）、`lastModified`（时间戳）、`status`（`pending` | `uploading` | `success` | `failed` | `oversized`）、`failCount`（0–3）、`lastError`（最后一次错误描述）、`selected`（是否选中）、`parentId`（所属目录 ID 或 null）。`File` 对象本身不序列化到 Session Storage，仅在内存中持有。
- **BatchDeleteRequest**: 代表一次批量删除请求，关键属性：`ids`（图片 ID 数组，上限 500）。
- **UploadBatch**: 单次上传批次，最多包含 3 个 `QueueEntry`，串行执行。

## 成功标准 *(mandatory)*

### 可衡量结果

- **SC-001**: 用户能在 2 次点击内完成批量删除操作（选中 → 删除按钮 → 确认），删除后列表即时更新，无需手动刷新。
- **SC-002**: 上传队列页面能正确展示选择的文件信息（名称、大小、修改时间），准确率 100%（无错误展示）。
- **SC-003**: 单次上传批次严格限制在最多 3 个并发请求，不超出此限制（可通过网络请求监控验证）。
- **SC-004**: 在网络不稳定场景下，失败文件在用户手动重新触发上传后能成功重试；达到 3 次失败上限后不再自动或手动触发新请求。
- **SC-005**: 页面刷新后，成功/失败/禁用状态从 Session Storage 正确恢复，无误差（`parent_id` 相同场景下）。
- **SC-006**: 同一目录下的同名文件重复添加到队列时，100% 被客户端拦截，不发出重复上传请求。
- **SC-007**: 批量删除功能的 E2E 测试用例和上传队列的关键路径单元/集成测试覆盖率达到主要用户场景的 80% 以上。

## 假设

- 图片选择器仅支持图片类型（`image/*`），不支持选择目录；此限制由文件选择器属性和服务端校验共同保障。
- 浏览器 `File.lastModified` 属性在主流现代浏览器（Chrome、Firefox、Safari）中均可用，可作为文件修改时间的主要来源；不依赖更复杂的 File System Access API `showOpenFilePicker`（避免浏览器兼容性问题）。
- 每批最多 3 张图片，批次内并发上传（即同时发出最多 3 个请求），批次间串行（上一批全部完成才开始下一批）。
- Session Storage 的配额在目标用户的设备上足够存储队列元数据（文件名、大小、状态等纯文本数据，通常远小于 5 MB 限额）。
- 批量删除弹窗不需要再列出图片缩略图预览，仅展示选中数量和警告提示即可（与批量发布状态弹窗风格一致）。
- `parent_id` 为 `null` 时（根目录）在 Session Storage 中以固定字符串 `"root"` 作为键的一部分，避免与 `undefined` 混淆。
- 删除 API 使用独立的批量删除路由（`DELETE /[lang]/console/api/images/batch`），不复用现有的 `PATCH` 批量路由，职责分离更清晰。
- 上传队列页面刷新后，已记录在 Session Storage 的条目可恢复状态（成功/失败/选中），但 `File` 对象无法从 Session Storage 恢复；因此已成功或超限失败的条目不受影响（禁用），其余需要用户重新选择文件才能再次上传（可在 UI 中给出明确提示）。
