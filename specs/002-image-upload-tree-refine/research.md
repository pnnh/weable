# Phase 0 研究结论：控制台图片批量上传与树形列表优化

## 决策 1：上传接口采用单端点批量提交（同名 multipart 字段）

- Decision: 继续使用 `POST /api/upload`，通过 `multipart/form-data` 的同名字段 `file` 提交多文件（一次最多 50 个），`parentId` 维持为可选字段。
- Rationale: 兼容现有上传链路（前端 FormData + 后端 route.ts）；改动最小，不引入新接口；可直接复用现有目录归属校验。
- Alternatives considered:
  - 新增 `POST /api/uploads/batch`：语义清晰，但增加路由与维护成本。
  - 前端循环 50 次单文件上传：网络开销与失败处理复杂，不满足“整批体验”。

## 决策 2：批量上传限制采用“数量+单文件大小”双重校验，失败按整批失败处理

- Decision: 单次最多 50 张，单文件最大 5 MB；任一文件不合规则阻止本批次提交，返回明确错误。
- Rationale: 与规格中的“整批校验、整批提交”假设一致；避免部分成功导致用户误判和目录内容不一致感知。
- Alternatives considered:
  - 部分成功部分失败：可提升吞吐，但用户理解成本高，后续补传复杂。
  - 仅服务端校验：可行但反馈滞后，用户体验差。

## 决策 3：上传成功后返回列表页并保留目录上下文

- Decision: 上传成功后不跳转图片编辑页，直接返回 `/{lang}/console/images`；若存在 `parentId`，返回 `/{lang}/console/images?parentId=...`，并触发列表刷新显示新内容。
- Rationale: 直接满足用户目标（连续上传/管理）；保持目录上下文，避免多层目录中反复定位。
- Alternatives considered:
  - 跳转到首张图片详情页：不符合需求且打断批量上传节奏。
  - 仅前端局部插入新行不刷新：实现复杂度更高且与当前页面数据加载模式不一致。

## 决策 4：树形表格展开采用“固定控件占位 + 层级缩进”

- Decision: 目录左侧展开控件区域固定宽高占位（含未展开/无子项时的占位一致性），子级以统一步长缩进渲染，确保展开前后同列对齐稳定。
- Rationale: 当前偏移问题根因是控件列宽与动态缩进冲突；将控件占位固定化可消除视觉抖动并增强层级可读性。
- Alternatives considered:
  - 仅增大当前控件列宽：对深层级不稳健，仍可能溢出。
  - 用非表格容器重写列表：改动范围过大，不符合“精准手术式修改”。

## 决策 5：国际化与可观测反馈沿用现有模式

- Decision: 限制提示、上传中状态、错误提示均使用现有 i18n 词条机制扩展，不引入新提示系统。
- Rationale: 代码库已具备多语言资源结构，复用可降低回归风险。
- Alternatives considered:
  - 临时硬编码文案：会破坏多语言一致性。
  - 新增独立提示组件系统：超出本期范围。
