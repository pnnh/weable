# Feature Specification: 控制台图片批量上传与树形列表优化

**Feature Branch**: `002-image-upload-tree-refine`

**Created**: 2026-08-02

**Status**: Draft

**Input**: User description: "现在将 /en/console/images 页面的上传图片功能改造，允许选择多张图片（最多50张，大小5M以内）。上传成功后不再跳转至图片编辑页面而是返回图片列表并刷新。注意是返回当前目录层级所在的列表页面（注意保留 parentId 参数）。同时处理 /en/console/images 页面布局中的样式问题。首先目录左侧三角图标占用的宽高应该是固定的，但是现在当展开子级后三角图标的宽度似乎变更宽了，导致目录项向右侧发生了偏移，交互体验上不太好。另外当点击目录左侧三角形展开下级时列表应该是以一个树形表格形式呈现（子级需要缩进）而不是像现在这样仅仅展开子级。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 当前目录内批量上传图片 (Priority: P1)

控制台用户在图片列表页中，能够一次选择多张图片并提交上传，系统将图片保存到当前浏览层级，并在上传完成后返回当前目录列表刷新显示新结果。

**Why this priority**: 批量上传直接影响图片录入效率，是本次需求中最核心的业务价值；若此能力不可用，其余列表优化无法弥补操作成本。

**Independent Test**: 在根目录或任意子目录列表页中，单独验证一次选择多张图片上传，确认上传后仍停留在当前目录列表，并能看到新图片出现在该层级。

**Acceptance Scenarios**:

1. **Given** 用户位于根目录图片列表页，**When** 一次选择 2 到 50 张且每张不超过 5 MB 的图片并提交上传，**Then** 系统完成上传后返回根目录列表页并刷新列表显示新增图片。
2. **Given** 用户位于某个子目录列表页，**When** 一次选择多张符合限制的图片并提交上传，**Then** 系统完成上传后返回该子目录对应的列表页，并保留当前目录标识参数。
3. **Given** 用户已选择 51 张图片，**When** 尝试提交上传，**Then** 系统阻止提交并明确提示最多只能上传 50 张图片。
4. **Given** 用户已选择多张图片且其中任意一张超过 5 MB，**When** 尝试提交上传，**Then** 系统阻止提交并明确提示超限文件不符合大小要求。
5. **Given** 用户已提交一批合法图片，**When** 上传过程完成，**Then** 系统不跳转到任何单张图片详情或编辑页面。

---

### User Story 2 - 维持目录上下文返回列表 (Priority: P1)

用户无论在根目录还是任意子目录发起上传，上传完成后的页面位置都应保持在原先浏览的目录层级，避免丢失当前上下文。

**Why this priority**: 如果上传后丢失当前目录位置，用户需要重新定位目录，特别是在多层目录中会显著增加操作成本。

**Independent Test**: 从带有当前目录标识参数的列表页进入上传流程并完成上传，验证页面回到相同层级而不是根目录或详情页。

**Acceptance Scenarios**:

1. **Given** 用户从某个子目录列表页发起上传，**When** 上传成功，**Then** 返回地址仍指向该子目录列表页且当前目录标识参数未丢失。
2. **Given** 用户从根目录列表页发起上传，**When** 上传成功，**Then** 返回根目录列表页且不会附加无效的目录标识参数。
3. **Given** 用户在上传完成后查看列表内容，**When** 页面刷新完毕，**Then** 当前层级的图片列表与上传前相比已包含新上传的图片。

---

### User Story 3 - 树形表格稳定展开目录 (Priority: P2)

用户在图片列表页点击目录左侧的展开控件后，应以树形表格方式查看子级内容，子级相对父级有明确缩进，并且展开前后目录行的对齐关系保持稳定。

**Why this priority**: 树形结构的可读性和稳定对齐直接决定目录浏览体验；当前展开后视觉偏移会干扰用户对层级关系的判断。

**Independent Test**: 在存在多级目录的数据下，仅测试列表展开交互，确认子级以缩进方式呈现，且同层级目录在展开前后不会发生横向跳动。

**Acceptance Scenarios**:

1. **Given** 列表中存在子目录，**When** 用户点击目录左侧展开控件，**Then** 该目录的直接子项以内联树形表格方式显示在父项下方，并相对父项产生明确缩进。
2. **Given** 某目录已展开，**When** 用户再次点击其左侧展开控件，**Then** 该目录的子项折叠隐藏，父级与同级项目的横向对齐保持不变。
3. **Given** 列表中同时存在可展开目录、空目录和图片项，**When** 用户浏览列表并展开任意目录，**Then** 各行左侧控件占位保持固定，未展开项和展开项不会因为控件宽高变化产生额外偏移。
4. **Given** 已展开目录下存在子目录，**When** 用户继续展开子目录，**Then** 第二层及更深层级继续按树形层级递进缩进显示。

---

### User Story 4 - 清晰反馈上传限制与结果 (Priority: P3)

用户在选择文件和提交上传时，能够清楚理解数量与大小限制，并在不符合要求时立即获得可操作的反馈。

**Why this priority**: 明确反馈可减少重复试错，降低因大批量选择文件后提交失败带来的挫败感。

**Independent Test**: 仅测试文件选择与校验反馈，无需依赖目录树展开功能即可验证本故事价值。

**Acceptance Scenarios**:

1. **Given** 用户打开上传区域，**When** 查看上传控件说明，**Then** 可以看到单次最多 50 张、单张不超过 5 MB 的限制提示。
2. **Given** 用户选择了不符合规则的文件集，**When** 系统完成校验，**Then** 在提交前给出明确错误说明，提示用户调整选择内容。
3. **Given** 用户选择了符合规则的文件集并开始上传，**When** 上传进行中，**Then** 用户可以明确感知上传正在处理，避免重复提交。

### Edge Cases

- 用户一次未选择任何文件时，系统应阻止提交且保持当前页面不变。
- 用户一次选择的文件数量超过 50 张时，系统应在开始上传前阻止该批次提交。
- 用户选择的多张文件中仅部分超出 5 MB 时，系统应明确指出该批次不符合要求，避免用户误以为已完成部分上传。
- 用户在子目录层级上传完成后刷新浏览器，系统仍应停留在当前目录层级对应的列表页面。
- 某目录没有子项时，展开后应维持树形结构的一致表现，不应导致行布局错位。
- 多层目录连续展开时，各层级缩进应保持可辨识，不应出现子级与父级视觉混淆。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 允许用户在控制台图片上传流程中一次选择多张图片进行上传。
- **FR-002**: 系统 MUST 将单次可上传图片数量限制为最多 50 张，并在超出限制时阻止提交。
- **FR-003**: 系统 MUST 将每张图片大小限制为不超过 5 MB，并在任意选中文件超限时阻止该批次提交。
- **FR-004**: 系统 MUST 在上传入口清楚展示本次上传的数量与单文件大小限制。
- **FR-005**: 系统 MUST 在上传处理期间向用户呈现进行中的状态，避免重复提交。
- **FR-006**: 系统 MUST 将上传的所有图片保存到用户发起上传时所在的当前目录层级。
- **FR-007**: 系统 MUST 在上传成功后返回图片列表页，而不是进入单张图片详情或编辑页面。
- **FR-008**: 系统 MUST 在上传成功后保留用户原本所在的目录层级上下文；若上传前位于子目录，则返回时保留当前目录标识参数，若上传前位于根目录，则返回根目录列表。
- **FR-009**: 系统 MUST 在返回列表页后刷新当前层级数据，使新上传图片立即可见。
- **FR-010**: 系统 MUST 在目录展开交互中以树形表格形式展示子级内容，并通过层级缩进清楚表达父子关系。
- **FR-011**: 系统 MUST 为每一行的左侧展开控件区域提供固定占位，使目录在展开前后保持稳定对齐。
- **FR-012**: 系统 MUST 在目录展开与折叠时保持同层级行内容的横向位置稳定，不因控件状态变化造成额外位移。
- **FR-013**: 系统 MUST 支持多层级目录逐层展开，且每深入一层都保持一致的缩进规则。
- **FR-014**: 系统 MUST 在目录无子项时保持列表结构一致，不因空结果破坏树形表格的布局稳定性。
- **FR-015**: 系统 MUST 在上传失败时保留用户当前目录上下文与已知限制说明，使用户可以在当前层级重新操作。

### Key Entities *(include if feature involves data)*

- **上传批次（Upload Batch）**: 用户在一次操作中选中的一组图片文件，包含文件数量、每个文件大小校验结果、所属目录层级以及整体上传状态。
- **当前目录上下文（Current Directory Context）**: 用户发起上传或浏览列表时所在的目录层级信息，用于决定上传归属位置以及上传成功后的返回列表位置。
- **树形列表节点（Tree Row Node）**: 图片列表中的单行展示实体，可表示目录或图片，包含层级深度、是否可展开、是否已展开以及对应的缩进展示信息。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户一次可成功提交并完成最多 50 张图片的上传，无需逐张重复操作。
- **SC-002**: 100% 的超数量或超大小批次会在开始上传前被拦截，并向用户显示明确原因。
- **SC-003**: 100% 的成功上传操作完成后，用户停留在上传前所在的同一目录层级列表页面。
- **SC-004**: 成功上传后，用户在首次列表刷新中即可看到本批次新增图片出现在正确目录层级。
- **SC-005**: 在包含多级目录的列表中，用户展开任意目录时，同层级目录名称列的横向位置保持一致，不出现可感知的额外跳动。
- **SC-006**: 在可展开目录场景下，用户能够在一次浏览中辨认父子层级关系，并通过缩进区分至少 3 层目录结构。

## Assumptions

- 本期仅扩展图片上传数量与大小限制，不包含对非图片文件类型的支持。
- 本期以“整批校验、整批提交”为默认规则；只要本批次中存在不符合限制的文件，则用户需调整后重新提交。
- 上传成功后的返回目标始终是发起上传时对应的图片列表页面，而不是任何详情、编辑或其他中间页面。
- 当前目录层级的判定依赖已有的目录上下文机制，本期只要求在返回列表时保持该上下文不丢失。
- 树形表格优化仅针对控制台图片列表页的层级展示与对齐体验，不包含排序、筛选或跨目录拖拽能力。
- 现有目录与图片数据结构可继续承载本期需求，无需为本期新增独立业务实体。
